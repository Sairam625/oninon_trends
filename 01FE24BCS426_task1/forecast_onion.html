What stands out in the raw data

  1. Several varieties per day. These aren't duplicates: Puna, Local, Telagi and "Other" are different grades priced on the same day. Telagi almost disappears in 2025. Mixing grades would create fake jumps, so I model Puna only.
  2. Date gaps. Sundays and holidays are routine. There are also long holes: all of December 2023 (32 days), 2 Mar → 27 Mar 2025 (26 days), 17 Aug → 1 Sep 2025 (16 days) and two 11–13 day gaps in Dec 2024.
  3. Arrivals unit break. From 18 Sep 2025 the arrivals jump from about 270 to 20–150 overnight and start carrying decimals (e.g. 27.79). Other datasets do report arrivals in tonnes rather than quintals, so this looks like a unit change, not a real 10× crash in supply.
  4. Arrivals missing for Jun–Jul 2024 even though prices exist.
  5. Spikes. Telagi p_max of ₹13,020 with modal ₹650 (2024-04-19) is a clear entry error, but it's outside the Puna series. In Puna, the Aug–Nov 2024 surge to ₹5,000 is real: it's visible across varieties and matches the national onion price spike that year. There are a few single-day dips/jumps (e.g. 2024-10-29: ₹2,000 between ~₹3,000 days).
  6. Flat stretches. Prices are quoted in round ₹50/₹100 steps, so short runs of identical modal prices are normal, not stale data.

# Causal forward-fill only (uses past values, never future ones)
df["days_since_obs"] = df.groupby(grp).cumcount()
df[["modal", "spread"]] = df[["modal", "spread"]].ffill()
df["qty_missing"] = df["qty"].isna().astype(int)
df["qty"] = df["qty"].ffill()

Choices and why

  • Missing dates → causal forward-fill on a daily grid, plus flags. On a closed day, the last traded price is the best available information. Rejected alternative: linear interpolation. It looks smoother, but it uses the price after the gap, so it leaks future information into features. Days inside long gaps (> 7 days) are never used as forecast origins or as scoring targets, and only real observed prices are scored.
  • Outliers → keep them, limit their influence. Most big moves in this series are real market moves (the 2024 surge), and those are exactly what a price forecaster must learn. Rejected alternative: a Hampel/rolling-median filter that clips spikes. It would flatten the genuine Aug–Nov 2024 surge, and it needs a centred window (future values). Instead I model log price, use rolling medians next to means, and train with an L1 (absolute-error) loss, which is less sensitive to single bad days.
  • Arrivals unit break → scale post-18-Sep-2025 values ×10. After scaling, Sep–Oct 2025 arrivals land in the same range as the same months in earlier years. A missing-arrivals flag covers Jun–Jul 2024.

3. Features (direct multi-horizon setup)¶

In [8]:
HMAX = 14

def make_features(d):
    """Features at forecast origin t. Uses only rows <= t."""
    f = pd.DataFrame(index=d.index)
    lp = d["lp"]
    for L in [0, 1, 2, 3, 7, 14, 28]:
        f[f"lp_lag{L}"] = lp.shift(L)
    for w in [7, 14, 28]:
        r = lp.rolling(w, min_periods=max(3, w // 2))
        f[f"lp_mean{w}"] = r.mean(); f[f"lp_med{w}"] = r.median(); f[f"lp_std{w}"] = r.std()
    f["lp_max28"] = lp.rolling(28, min_periods=14).max(); f["lp_min28"] = lp.rolling(28, min_periods=14).min()
    f["mom7"] = lp - lp.shift(7); f["mom28"] = lp - lp.shift(28)
    f["dev_med28"] = lp - f["lp_med28"]
    f["spread"] = d["spread"]
    lq = np.log1p(d["qty"])
    f["lq"] = lq; f["lq_mean7"] = lq.rolling(7, min_periods=3).mean(); f["lq_mean28"] = lq.rolling(28, min_periods=10).mean()
    f["lq_trend"] = f["lq_mean7"] - f["lq_mean28"]
    f["qty_missing"] = d["qty_missing"]; f["days_since_obs"] = d["days_since_obs"]
    return f

def add_calendar(X, target_dates):
    doy = target_dates.dayofyear
    X["doy_sin"] = np.sin(2 * np.pi * doy / 365.25); X["doy_cos"] = np.cos(2 * np.pi * doy / 365.25)
    X["dow"] = target_dates.dayofweek
    return X

feat = make_features(df)

def stack(d, feat, horizons=range(1, HMAX + 1)):
    """One row per (origin t, horizon h). Target = log-price change from t to t+h."""
    rows = []
    for h in horizons:
        X = feat.copy(); X["h"] = h
        tgt_date = d.index + pd.Timedelta(days=h)
        X = add_calendar(X, tgt_date)
        X["origin"] = d.index; X["target_date"] = tgt_date
        X["y"] = d["lp"].shift(-h) - d["lp"]
        X["y_observed"] = d["observed"].shift(-h, fill_value=False).values
        X["origin_ok"] = (~d["in_long_gap"]).values
        rows.append(X)
    return pd.concat(rows, ignore_index=True)

data = stack(df, feat)
# Keep only rows with complete features, a usable origin and a REAL observed target price
data = data[data["origin_ok"] & data["y_observed"]].dropna().reset_index(drop=True)
FEATS = [c for c in data.columns if c not in ("origin", "target_date", "y", "y_observed", "origin_ok")]
print(len(FEATS), "features; rows:", len(data), "| origins:", data.origin.nunique())
print(FEATS)

Why these features

  • Lags and rolling stats of log price: onion prices are strongly persistent, so recent level and momentum carry most of the signal. Medians sit next to means for robustness to one-off spikes.
  • Arrivals (log, 7 vs 28-day trend): a supply proxy. Rising arrivals usually push prices down a little later.
  • Min–max spread: wide spreads signal mixed quality or volatile trading days.
  • Seasonality of the target date (day-of-year sin/cos, weekday): onion follows a harvest cycle (cheap Mar–May, dear Sep–Nov). The calendar of a future date is known in advance, so this is legitimate.
  • Horizon h and days-since-last-observation: let one model serve all 14 horizons and know how stale its latest price is.

The target is the log change from the origin to t+h, not the raw price. That keeps the target stationary and makes "no change" the natural default.

4. Model and 14-day forecast¶

In [10]:
PARAMS = dict(objective="l1", learning_rate=0.03, n_estimators=600, num_leaves=15, min_child_samples=30,
              subsample=0.8, subsample_freq=1, colsample_bytree=0.8, reg_lambda=1.0, random_state=SEED, verbose=-1)

def fit(train):
    m = lgb.LGBMRegressor(**PARAMS); m.fit(train[FEATS], train["y"]); return m

def to_price(rows, pred_logchange):
    return np.exp(rows["lp_lag0"].values + pred_logchange)

def scores(rows, pred_logchange):
    actual = np.exp(rows["lp_lag0"].values + rows["y"].values)
    p = to_price(rows, pred_logchange)
    return dict(MAE=np.mean(np.abs(p - actual)), MAPE=100 * np.mean(np.abs(p - actual) / actual))

# (a) Walk-forward: expanding window, 5 test blocks of 60 origins each at the end of the series.
#     Training rows are restricted so every training target date is before the first test origin (no overlap).
origins = np.sort(data.origin.unique())
n_folds, block = 5, 60
wf_rows, wf_pred, fold_log = [], [], []
for k in range(n_folds):
    test_start = origins[len(origins) - (n_folds - k) * block]
    test_end = origins[min(len(origins) - 1, len(origins) - (n_folds - k - 1) * block - 1)]
    tr = data[data.target_date < test_start]   # every training TARGET is before the first test origin
    te = data[(data.origin >= test_start) & (data.origin <= test_end)]
    m = fit(tr); pr = m.predict(te[FEATS])

wf_te = pd.concat(wf_rows); wf_pr = np.concatenate(wf_pred)

# Where does the random split's advantage come from? Drop the day-of-year features and re-run both evaluations.
def evaluate(feats):
    o = np.sort(data.origin.unique()); R, P = [], []
    for k in range(n_folds):
        ts = o[len(o) - (n_folds - k) * block]; te_end = o[min(len(o) - 1, len(o) - (n_folds - k - 1) * block - 1)]
        tr = data[data.target_date < ts]; te = data[(data.origin >= ts) & (data.origin <= te_end)]
        m = lgb.LGBMRegressor(**PARAMS).fit(tr[feats], tr["y"]); R.append(te); P.append(m.predict(te[feats]))
    wf = scores(pd.concat(R), np.concatenate(P))["MAE"]
    m = lgb.LGBMRegressor(**PARAMS).fit(tr_r[feats], tr_r["y"]); rd = scores(te_r, m.predict(te_r[feats]))["MAE"]
    return round(wf, 1), round(rd, 1)
no_doy = [f for f in FEATS if f not in ("doy_sin", "doy_cos")]
abl = pd.DataFrame([evaluate(FEATS), evaluate(no_doy)], index=["all features", "without day-of-year"],
                   columns=["walk-forward MAE", "random-split MAE"])
print(abl.to_string())

                     walk-forward MAE  random-split MAE
all features                    263.1             114.4
without day-of-year             264.8             139.7

Why the random split looks so much better. In a random split, the test row for, say, origin 14 Oct, h = 3 sits among training rows for 13 Oct and 15 Oct at nearby horizons. Those rows share almost all the same features and overlapping target days, so the model has effectively seen the answer. The ablation above shows it directly: removing the day-of-year features barely changes the walk-forward error, but the random-split error rises sharply. In a random split, day-of-year works like a lookup key for "which neighbouring day's answer to copy". Because the order of time is ignored, it also trains on 2025 rows when predicting 2023. The walk-forward number is the honest one, because it's what you'd get running the model in production. The random-split number mostly measures interpolation, not forecasting.
